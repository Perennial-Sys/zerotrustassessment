## Category

## Risk Level

High - Without rate limiting rules configured, web applications are vulnerable to brute force attacks, credential stuffing, API abuse, and denial of service attacks that can overwhelm backend resources by sending excessive requests from individual clients or IP addresses.

## User Impact

Low - Enabling rate limiting is transparent to legitimate users operating within normal request thresholds and requires no action or notification beyond administrative configuration.

## Implementation Cost

Medium - Activation involves creating custom rate limiting rules in the Application Gateway WAF policy, which requires understanding of application traffic patterns to set appropriate thresholds that protect against attacks while not blocking legitimate users.

## Customer Facing Explanation

Azure Application Gateway Web Application Firewall (WAF) supports rate limiting through custom rules that restrict the number of requests clients can make within a specified time window. Rate limiting is a critical defense mechanism that protects applications from abuse by throttling clients that exceed defined request thresholds. Without rate limiting configured, threat actors can execute brute force attacks that attempt thousands of password combinations per minute against authentication endpoints, credential stuffing attacks that test stolen credentials at scale, API abuse that extracts large volumes of data or consumes expensive backend resources, and application-layer denial of service attacks that flood endpoints with requests to exhaust server capacity. Rate limiting rules use the `RateLimitRule` rule type and allow administrators to define thresholds based on request count per minute, with the ability to group requests by client IP address (using `groupBy` with `ClientAddr` variable) to track and limit individual clients. When a client exceeds the configured threshold, the WAF can block subsequent requests, log the violation, or redirect to a custom page. Unlike managed rulesets that detect attack patterns, rate limiting provides a quantitative defense that limits the impact of any volumetric attack regardless of whether the individual requests appear malicious. By configuring rate limiting on Application Gateway WAF, organizations can ensure that no single client can monopolize application resources or execute high-volume automated attacks.

### Step 3: Exclude any Azure Application Gateway policies which are not attached to an Azure Application Gateway

**Filtering Logic:**

For each WAF policy returned in Step 2, check the `properties.applicationGateways` array:

- **Include** policies where `properties.applicationGateways` array contains at least one entry (policy is attached to an Application Gateway)
- **Exclude** policies where `properties.applicationGateways` array is empty or missing (policy is not actively protecting any Application Gateway)

**Example:**
- `WAFPol01`: Has `applicationGateways` array with entry -> **Include in evaluation**
- `WAFPol02`: Has `applicationGateways` array with entry -> **Include in evaluation**
- `WAFPol03-Unattached`: Has empty `applicationGateways` array -> **Exclude from evaluation**

**What to look for:**
- Check `properties.customRules` array for each WAF policy
- The array must contain at least one rule with `ruleType` of `RateLimitRule` and `state` set to `Enabled`
- An empty `customRules` array or no rules with `ruleType: "RateLimitRule"` indicates rate limiting is not configured

## User Facing Message

**Pass**: All Application Gateway WAF policies attached to Application Gateways have at least one rate limiting rule configured and enabled.

**Fail**: One or more Application Gateway WAF policies attached to Application Gateways do not have any rate limiting rules configured, leaving applications vulnerable to brute force and volumetric attacks.

**Skip**:
1. No subscription found or the signed in user does not have access to the Azure subscription to perform this test.
2. The user is not connected to Azure.
3. No Application Gateway WAF policies attached to Application Gateways found across subscriptions.

## Test Evaluation Logic

- **Filter**: Only evaluate WAF policies where `properties.applicationGateways` array contains at least one entry (policies attached to an Application Gateway)

- **Exclude**: WAF policies where `properties.applicationGateways` is empty or missing are excluded from evaluation

- **Pass**: All filtered Application Gateway WAF policies have `customRules` array containing at least one rule where `ruleType` equals `RateLimitRule` and `state` equals `Enabled`

- **Fail**: Any filtered Application Gateway WAF policy has either:
  1. An empty `customRules` array, or
  2. No rules with `ruleType` of `RateLimitRule`, or
  3. All rate limit rules have `state` set to `Disabled`

## Challenges

**Required Permissions:**
- `Microsoft.Network/ApplicationGatewayWebApplicationFirewallPolicies/read` - Required to read Application Gateway WAF policy configurations
- `Microsoft.Resources/subscriptions/read` - Required to list subscriptions

**Required Roles:**
- Network Contributor or Reader role on subscriptions containing Application Gateway WAF policies

**Known limitations:**
- Rate limiting rules require WAF_v2 SKU on Application Gateway; v1 SKU does not support rate limiting
- Rate limit rules use `rateLimitDuration` with values like `OneMin` or `FiveMins` to define the time window for counting requests
- The `rateLimitThreshold` defines the maximum number of requests allowed in the duration window before the action is triggered
- Rate limiting is most effective when combined with `groupByUserSession` using `ClientAddr` to track requests per client IP
- Setting thresholds too low may block legitimate high-volume users; requires understanding of normal application traffic patterns
- Rate limiting rules can be scoped to specific endpoints using match conditions on `RequestUri`
- This check validates that at least one rate limit rule exists and is enabled; it does not evaluate threshold appropriateness
- Rate limiting works best in conjunction with managed rulesets (OWASP or Microsoft_DefaultRuleSet) for comprehensive protection
- This check only evaluates WAF policies that are attached to Application Gateways; unattached policies are excluded from evaluation as they are not actively protecting any resources
